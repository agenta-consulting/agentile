# Agentile plugin review — against current Claude Code documentation

Review date: 2026-06-13. Reviewed: the full plugin source at `company/internal_projects/lean_agentic_loop/` (all 13 skills, 3 agents, 4 hooks, 4 bin helpers, all templates, the manifest, and the four design docs), checked against the official Claude Code docs at code.claude.com/docs (pages cited inline: [plugins reference](https://code.claude.com/docs/en/plugins-reference), [skills](https://code.claude.com/docs/en/skills), [subagents](https://code.claude.com/docs/en/sub-agents), [hooks](https://code.claude.com/docs/en/hooks), [scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks), [/goal](https://code.claude.com/docs/en/goal), [memory](https://code.claude.com/docs/en/memory), [commands](https://code.claude.com/docs/en/commands)). No plugin files were modified.

## Executive summary

The plugin is a faithful, well-structured implementation of the Lean Agentic Loop, and its two cleverest pieces — the atomic `ag-claim` pull and the uniform per-stage playbook contract — are genuinely good design that the official docs have no native equivalent for. The loop architecture (`/ag-loop` one pass, `/loop /ag-loop` continuous) is the right pattern: `/loop` is confirmed as a documented bundled skill with exactly the self-paced semantics the README assumes. However, the review found one outright defect and a cluster of staleness issues: **both gate hooks read `.lal/gates.json` instead of `.agentile/gates.json`, so the plugin's flagship "deterministic gates" feature has been silently dead since the rename**; the pinned `version: 0.1.0` means marketplace installs never receive any of the 36 commits of improvements; and several mechanisms (the SessionStart session-id hook, the cache-glob helper resolution, the "Claude Code can't set a session name" claim) were built on doc research that is now superseded — `${CLAUDE_SESSION_ID}` is a documented skill substitution variable, plugin `bin/` executables land on the Bash PATH automatically, and SessionStart hooks can set `sessionTitle`. The bootstrap story is the weakest part of the methodology fit: the triage tells users to score Business Value "against current priorities", but no artefact ever records what those priorities are — a project brief, captured at `/ag-init` time, would close that loop.

## Question 1 — The loop: is `/ag-loop` + `/loop /ag-loop` the right pattern?

### Verdict

**Yes — the split is correct, well-explained, and matches current capabilities — but it has three undocumented robustness gaps, and two newer constructs (`/goal` and `FileChanged`/monitor watching) should be evaluated as upgrades.**

`/loop` is confirmed as a bundled skill: "Run a prompt repeatedly while the session stays open. Omit the interval and Claude self-paces" ([commands](https://code.claude.com/docs/en/commands)). Passing a command as the prompt (`/loop 20m /review-pr 1234`) is an explicitly documented usage ([scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks)), so `/loop /ag-loop` is idiomatic, not a hack. The skill's loop body discipline (cheap idle ticks, "never stop silently", resume-check before claiming, state living in spec frontmatter) is exactly what the scheduled-tasks docs ask of a good loop body. The drain/watch documentation in the README and `templates/CLAUDE.agentile-section.md` is unusually clear.

### Robustness gaps (not currently documented by the plugin)

- **Seven-day expiry.** Recurring `/loop` tasks "automatically expire 7 days after creation" — a standing watch loop silently dies after a week ([scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks#seven-day-expiry)). The README's "standing worker" framing should carry this caveat.
- **Permission prompts.** `/loop` "inherits permission prompts from the session" (scheduling comparison table). An unattended watch loop will stall at the first un-allowlisted tool call, which in a build cycle is almost immediate. The plugin says nothing about permission posture; it should document running watch mode under [auto mode](https://code.claude.com/docs/en/goal) or with pre-seeded `permissions.allow` (the gates commands in `gates.json` are the obvious allowlist candidates), and note that `allowed-tools` in skill frontmatter only covers the skill's own turn.
- **Session lifetime.** Tasks "only fire while Claude Code is running and idle. Closing the terminal stops them" — and `Esc` while waiting clears the loop. Combined with expiry, "the loop never stops silently" is true within a turn but not across the session lifecycle.

### Constructs to evaluate

- **`/goal` for drain mode.** `/goal` "sets a completion condition and Claude keeps working across turns until the condition is met", with a fresh small-model evaluator after each turn ([/goal](https://code.claude.com/docs/en/goal)). Today `/ag-loop` drains up to `max_iterations` items *inside one turn*, which strains the context window and compaction across multiple full build cycles. `/goal the specs queue at docs/agentile/specs/ has no claimable ready spec, or stop after N items` gets fresh turns per cycle and a doc-sanctioned stop condition. The docs' own comparison table (`/goal` vs `/loop` vs Stop hook) maps almost perfectly onto drain vs watch vs gate. At minimum, `ag-loop` could recommend `/goal` for long drains; pause-before-ship still works because a pause turn fails the goal condition without ending it.
- **Event-driven watching instead of polling.** Two native mechanisms now exist: a SessionStart hook can return `watchPaths` and a **`FileChanged` hook** fires when a watched file changes ([hooks](https://code.claude.com/docs/en/hooks)); and plugins can ship **monitors** (`monitors/monitors.json`) — persistent background scripts that stream output into the session ([plugins reference](https://code.claude.com/docs/en/plugins-reference#monitors)). Watching `docs/agentile/specs/` (or `inbox.md`) would start work the moment a spec lands, with zero idle-tick token cost. This is a stronger "standing worker" than interval polling and worth a design spike.
- **`.claude/loop.md` integration.** A bare `/loop` runs the project's `.claude/loop.md` prompt if present ([scheduled tasks](https://code.claude.com/docs/en/scheduled-tasks#customize-the-default-prompt-with-loop-md)). `/ag-init` should offer to write a one-line `.claude/loop.md` ("Run /ag-loop.") so plain `/loop` does the right thing in an Agentile project — and the docs must then disambiguate `.claude/loop.md` (the prompt) from `.agentile/loop.md` (the policy), which is a near-certain user confusion.
- **Unattended runs** remain correctly out of scope; [routines](https://code.claude.com/docs/en/scheduled-tasks#compare-scheduling-options) (`/schedule`) are the documented path and the design doc already says so.

### Recommendation

Keep the two-command pattern and its documentation. Add a "running unattended" section covering the 7-day expiry, permission posture, and session lifetime. Prototype `/goal`-based draining and `FileChanged`/monitor-based watching as v2 candidates; scaffold `.claude/loop.md` from `/ag-init`.

## Question 2 — Agent customisation: is ag-customise the right mechanism?

### Verdict

**Yes for stage *content* — the playbook contract is uniform, discoverable, and conversational, and it's a better fit for methodology tailoring than raw Claude Code config. But the plugin hides the documented native override path for the agents themselves, and its hard-coded `model: opus` makes that omission expensive.**

What works:

- The `.agentile/<stage>.md` contract (`delegate_to`, `also_run`, `human_checkpoint`, prose policy) is applied consistently across every skill and both playbook-reading agents, with identical preamble text, so behaviour is predictable. `/ag-customise` interviewing the user and writing the file mirrors how the docs recommend turning recurring instructions into files rather than chat ([memory](https://code.claude.com/docs/en/memory#when-to-add-to-claude-md)).
- Project-level config in checked-in files matches Claude Code convention (project skills/rules/settings are all repo files shared via version control).

What's missing or fights convention:

- **Native agent overrides are undocumented by the plugin.** Subagent precedence is explicit in the docs: project `.claude/agents/` is priority 3, user `~/.claude/agents/` is priority 4, and a plugin's `agents/` directory is priority 5 (lowest) — "when multiple subagents share the same name, the higher-priority location wins" ([subagents](https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope)). So any user can already fork `ag-builder` into `.claude/agents/ag-builder.md` and change its model, tools, effort, or prompt, per project or per user. The README's "the methodology core… you don't fork them" framing is philosophically fine but should name this escape hatch, because it is *the* Claude Code way to customise an agent and it works today with zero plugin support.
- **`model: opus` is pinned in all three agents** (`agents/ag-builder.md`, `ag-planner.md`, `ag-reviewer.md`). The documented default is `inherit`, and the docs position model choice as a cost control ([subagents](https://code.claude.com/docs/en/sub-agents#choose-a-model)). Pinning the most expensive model for every plan/build/review, with no `.agentile/` knob to change it, forces users into the fork-the-agent path the README discourages. Either inherit, or expose model per stage in the playbooks and have the skills pass it through.
- **No user-level tier.** `.agentile/` is project-only; a consultant running Agentile across many repos re-answers the same `/ag-customise` interviews. A `~/.agentile/` fallback (project wins) would mirror the user/project split used by skills, agents, and rules.
- **Minor overlap with native skill features.** `delegate_to` re-implements what a skill's own `agent`/`context: fork` frontmatter partially covers ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)); the bespoke contract is justified because it's per-project rather than per-skill, but the docs comparison belongs in `playbooks.md` so users understand why.

### Recommendation

Document the `.claude/agents/` override path explicitly (README + `/ag-customise`, which should offer "override the agent definition" as an option for the build/verify stages). Change the agents to `model: inherit` or make model a playbook directive. Consider a `~/.agentile/` user tier.

## Question 3 — Fresh project bootstrap

### Verdict

**The bootstrap story is the plugin's weakest area. Recommendation: brief-first, then stories — and the plugin should add a project-brief artefact, because the methodology already depends on one that doesn't exist.**

Current state: `/ag-init` scaffolds config and points at `/init` for `CLAUDE.md`; on a brand-new empty repo the user is then expected to `/ag-capture` stubs into an inbox with no surrounding context. Three concrete problems:

- **The triage has no reference point.** `templates/agentile/config.md` instructs: score Business Value "against current priorities, not gut feel" — but nothing in the system records what the current priorities *are*. On a greenfield project there is no code, no CLAUDE.md of substance, and no ADRs, so `/ag-shape`'s interview and `/ag-prioritise`'s BV×TC proposal both run on vibes. The methodology essay itself names "Standing context (set up once)" as step 0 and "a living project brief" as its content (`lean-agentic-loop.md` §0) — the plugin implements every step except this one.
- **`/init` doesn't cover it.** `/init` generates CLAUDE.md *from the existing codebase* ([memory](https://code.claude.com/docs/en/memory#set-up-a-project-claude-md)); on an empty repo it has nothing to read. (Worth noting: `CLAUDE_CODE_NEW_INIT=1` enables an interactive multi-phase `/init` that asks questions and proposes artefacts — the exact interview pattern Agentile should emulate.)
- **Stories-first on a green field produces incoherent specs.** Each shaped spec captures problem/acceptance/scope for *itself*, but cross-cutting choices (stack, architecture, target users, the outcome metric) get re-litigated per spec or silently assumed by the planner.

Recommended bootstrap flow (brief-first, then iterate with stories):

1. `/ag-init` detects a fresh project (no CLAUDE.md of substance, empty repo) and offers an **interview mode**: who is this for, what outcome matters first, constraints, stack preference, what "shipped v1" looks like. Output: `docs/agentile/brief.md` (vision, users, prioritised outcomes, constraints, explicit non-goals) — exactly the "living project brief" the essay calls for. The stack decision seeds `docs/adr/0001-…`.
2. The CLAUDE.md Agentile section gains one line pointing at the brief (or an `@docs/agentile/brief.md` import — imports are documented and load at launch, [memory](https://code.claude.com/docs/en/memory#import-additional-files); keep the brief short if imported, since CLAUDE.md adherence drops past ~200 lines).
3. `/ag-shape`, `/ag-spec`, `/ag-prioritise`, and `ag-planner` add "read the brief" to their standing-context step — Business Value is then scored *against the brief's outcomes*, which fixes the dangling reference in `config.md`.
4. Offer to **seed the inbox from the brief**: a one-shot "split this brief into capture stubs" pass, then the normal shape → prioritise → loop machinery takes over. This keeps capture-is-free intact while giving day one a populated queue.
5. `/ag-retro`'s "encode the lessons" step should list the brief alongside CLAUDE.md and ADRs as an update target, so the brief stays living rather than becoming a launch document.

This needs at most one new artefact and one new interview (either inside `/ag-init` or as a separate `/ag-brief` so existing projects can adopt it); it does not change the loop.

## Question 4 — General best-practice audit

### Verdict

**Mostly conformant and in places exemplary (skill descriptions, ag-claim's tested core, opt-in-safe hooks as a design intent) — but one defect kills the hook feature outright, the version pin freezes all installed users, and several mechanisms are built on doc claims that are now stale.**

Highlights by area, with detail in the findings table below:

- **Skill frontmatter**: all 13 descriptions follow the documented pattern (what it does + when to use + trigger phrases) and sit at 236–386 characters, far under the 1,536-character listing cap ([skills](https://code.claude.com/docs/en/skills#frontmatter-reference)). `name` matches the directory everywhere. `$ARGUMENTS` usage is valid. Two gaps: no skill sets `disable-model-invocation: true`, which the docs recommend "for workflows with side effects or that you want to control timing" — `/ag-abandon` ("kill this work item"), `/ag-init`, and `/ag-prioritise` are exactly that class; and note `allowed-tools` *grants permission*, it does not restrict — the "Read-only" intent on `ag-inbox`/`ag-wip` is advisory unless `disallowed-tools` is used.
- **Command naming**: the `ag-` prefix is good hygiene; plugin skills surface as `/ag-*` with namespaced fallback on conflict, and none collide with bundled skills.
- **Manifest/marketplace**: valid. `"skills": "./skills/"` is redundant — the manifest `skills` key *adds to* the always-scanned default `skills/` directory ([plugins reference](https://code.claude.com/docs/en/plugins-reference#path-behavior-rules)). Missing optional metadata (`repository`, `homepage`, `displayName`) that the `/plugin` UI surfaces. `agents/`, `hooks/hooks.json`, and `bin/` all sit in their documented default locations and load automatically.
- **Hooks**: correct event choice and output schemas (`decision: block` for Stop, `hookSpecificOutput.additionalContext` for SessionStart), correct opt-in-safe philosophy — but the gates path bug (finding 1) means none of it currently runs, and the `stop_hook_active` loop guard reads a field no longer in the documented Stop input.
- **Subagent usage**: the planner/builder/reviewer split with fresh contexts is exactly what the subagents docs recommend, and `color` is a valid field. Missed natives: `isolation: worktree` (purpose-built for the builder), `memory` (cross-session learning for builder/reviewer), `skills` preloading, `maxTurns` as a runaway guard.
- **bin/ error handling**: helpers are tested (`ALL PASS` on both suites — verified during this review) and argument-checked, but a missing/typo'd specs dir produces a raw Ruby `Errno::ENOENT` stack trace from `ag-claim` (the lock-file open) and silent empty output from `ag-dependents`.
- **Version/update story**: broken in practice — see finding 2.

## Findings

### High severity

1. **Both gate hooks read the wrong config path — the deterministic-gates feature is dead.** `hooks/format-on-edit.rb:36` and `hooks/test-gate.rb:40` build `gates_path = File.join(cwd, '.lal', 'gates.json')` while everything else in the plugin — `/ag-init`, the agents, the templates, even these files' own header comments — uses `.agentile/gates.json`. Because both hooks are deliberately "no-op when config is missing", they exit silently on every project initialised by `/ag-init`: the formatter never runs and "done" is never blocked on failing tests. This is a leftover from the pre-rename `.lal` era and there is no test covering hook path resolution. **Fix:** change both to `.agentile/gates.json` (optionally falling back to `.lal/` for unmigrated projects, and have `/ag-init`'s migration mention it); add a hook test alongside `test-session-id.rb` that feeds a fake `cwd` and asserts the gate fires.
2. **Pinned `version: 0.1.0` freezes every marketplace install.** `.claude-plugin/plugin.json` sets an explicit version; per the docs, "users get updates only when you bump this field. Pushing new commits without bumping it has no effect, and `/plugin update` reports 'already at the latest version'" ([plugins reference](https://code.claude.com/docs/en/plugins-reference#version-management)). The repo has 36 commits and zero tags since 0.1.0, so anyone who installed from `agenta-consulting/agentile` is running the first snapshot forever. **Fix:** during active development, *omit* `version` so every commit is a new version (the documented pattern for "internal or team plugins under active development"); once stable, bump semver per release and tag. Note also that `bin/ag-dev-link` derives the cache path from this version, so changing strategy needs a matching tweak there.

### Medium severity

3. **`stop_hook_active` is no longer in the documented Stop-hook input.** `hooks/test-gate.rb:37` relies on it to avoid re-blocking in a loop; the current hooks reference lists the Stop input fields and this is not among them. If the field is gone, a repo whose tests *cannot* pass risks a block loop (the hook blocks, Claude tries, stops, gets blocked again). **Fix:** verify against a live session; if absent, implement the guard yourself (e.g. a per-session marker under `${CLAUDE_PLUGIN_DATA}`, the documented persistent plugin state directory) or cap consecutive blocks. ([hooks](https://code.claude.com/docs/en/hooks), [plugins reference](https://code.claude.com/docs/en/plugins-reference#environment-variables))
4. **Brittle helper/template resolution via cache-glob.** `ag-next` (step 3), `ag-abandon` (step 3), and `ag-init` (step 1) fall back to globbing `~/.claude/plugins/cache/agentile/agentile/*/…`. The cache layout is an internal detail; orphaned version directories linger for ~7 days after updates (the glob's "newest" pick can race a fresh install), and the docs warn the plugin-root path "changes when the plugin updates… treat it as ephemeral". The docs-native answer makes the whole dance unnecessary: **files in a plugin's `bin/` are added to the Bash tool's PATH and "invokable as bare commands… while the plugin is enabled"** ([plugins reference](https://code.claude.com/docs/en/plugins-reference#plugin-components-reference)). **Fix:** call `ag-claim` / `ag-dependents` as bare commands (keep one `${CLAUDE_PLUGIN_ROOT}` fallback at most); for `ag-init` templates, use the documented `${CLAUDE_SKILL_DIR}` substitution (`${CLAUDE_SKILL_DIR}/../../templates/`) instead of the cache glob ([skills](https://code.claude.com/docs/en/skills#inject-dynamic-context)).
5. **The session-id hook mechanism is superseded.** `${CLAUDE_SESSION_ID}` is now a documented substitution variable in skill content ([skills](https://code.claude.com/docs/en/skills#use-arguments)), so `ag-next`/`ag-loop` can embed the real session id directly instead of scanning injected context for "Agentile: this session's id is …" and minting a `whoami@host/timestamp` fallback — which is *not* a resumable handle, yet step 5 still tells the user to run `claude --resume <session-id>` with it. Relatedly, the customisation design doc's verified claim "there is no programmatic way to set the session name" is now false: SessionStart hooks can return `sessionTitle` ([hooks](https://code.claude.com/docs/en/hooks)). **Fix:** put `${CLAUDE_SESSION_ID}` in the ag-next/ag-loop skill bodies; either retire `hooks/session-id.rb` or repurpose it to set a recognisable `sessionTitle` (e.g. "agentile loop") so `/ag-wip` users can also find loops by name.
6. **`ag-builder` doesn't use native worktree isolation.** The docs provide `isolation: worktree` — "run the subagent in a temporary git worktree… automatically cleaned up if the subagent makes no changes" ([subagents](https://code.claude.com/docs/en/sub-agents#supported-frontmatter-fields)) — which is precisely the methodology's "give each agent its own worktree". The agent instead carries prose ("use an isolated worktree"), which the model may or may not act on. **Fix:** set `isolation: worktree` on `ag-builder` (or make it a `.agentile/build.md` directive the dispatching skill honours), and reconcile with the `worktree-workflow` `delegate_to` example so the two paths don't double-worktree.
7. **No `disable-model-invocation` on side-effectful skills.** The skills docs recommend it for "workflows with side effects or that you want to control timing, like /commit, /deploy" ([skills](https://code.claude.com/docs/en/skills#control-who-invokes-a-skill)). `/ag-abandon` (moves specs, strips dependencies — trigger phrase "kill this work item" is conversationally common), `/ag-init` (writes many files), and `/ag-prioritise` (mass-renames files) are all auto-invocable today. **Fix:** add `disable-model-invocation: true` to ag-init, ag-abandon, ag-prioritise (keep ag-capture/ag-inbox/ag-wip model-invocable — those triggers are the point); decide deliberately for ag-loop/ag-next (note: this also excludes a skill from subagent `skills:` preloading).
8. **The test gate runs the full suite on every Stop, including idle loop ticks.** With gates configured (post fix 1), every turn-end in the repo runs `test` — including each cheap "idle — nothing ready" tick under `/loop /ag-loop`, which defeats the "idle ticks are cheap" design, and `hooks.json` caps it at 180s which will kill longer suites mid-run (hook default is 600s, [hooks](https://code.claude.com/docs/en/hooks)). **Fix:** short-circuit when the working tree is clean (`git status --porcelain` empty → allow), and/or remember the tree-hash of the last green run; revisit the 180s timeout.
9. **`/ag-init`'s "Enable hooks?" question is a no-op.** Plugin hooks in `hooks/hooks.json` "merge with your user and project hooks" automatically when the plugin is enabled ([hooks](https://code.claude.com/docs/en/hooks)); a user answering "no" gets them anyway (they no-op only because `gates.json` is blank). Step 6 half-acknowledges this. **Fix:** reframe the question as "configure gate commands now?" and state plainly that the hooks are active-but-inert until commands are filled in.
10. **The claim mutex doesn't cover worktrees.** `bin/ag-claim`'s `flock` on `<specs>/.pull.lock` serialises sessions sharing one checkout, but each git worktree has its own copy of the specs tree — two loops in different worktrees can claim the same spec and the claims merge-conflict later. Since the methodology actively promotes worktree parallelism (and finding 6 recommends more of it), this is a real hole, not just the documented "cross-machine" limitation. **Fix:** document that claiming must happen in the shared main checkout (builders go to worktrees, the *backlog* doesn't), and state it in README's concurrency section; longer-term, resolve the specs dir relative to the main worktree (`git worktree list` / `git rev-parse --git-common-dir`).

### Low severity

11. **`ag-claim` frontmatter rewrite destroys comments.** `bin/ag-claim:69` re-serialises the whole frontmatter via `fm.to_yaml`, so the spec template's explanatory comments (`# Claim fields — set by /ag-next…`) vanish and keys reorder on first claim, producing noisy diffs. Fix: targeted line edits for the four claim fields, or accept and strip comments from the template.
12. **`.pull.lock` litters the specs directory.** It's created inside `docs/agentile/specs/` and never ignored. Fix: `/ag-init` adds `**/specs/.pull.lock` to `.gitignore`.
13. **`bin/ag-claim` stack-traces on a missing specs dir** (the lock-file `File.open` raises `Errno::ENOENT` before any friendly message), and `bin/ag-dependents` silently prints nothing for a bad dir — indistinguishable from "no dependents". Fix: `abort "ag-claim: no such specs dir: …"` guards in both.
14. **Manifest polish.** Drop the redundant `"skills": "./skills/"` (default `skills/` is always scanned; the key only *adds* directories — [plugins reference](https://code.claude.com/docs/en/plugins-reference#path-behavior-rules)); add `repository`, `homepage`, and `displayName` for the `/plugin` UI; run `claude plugin validate --strict` in CI (the flag exists for exactly this).
15. **`MultiEdit` in the PostToolUse matcher** (`hooks/hooks.json:5`) is no longer a documented tool name; harmless, but `Edit|Write|NotebookEdit` reflects the current tool set.
16. **Dev scripts ship onto users' PATH.** Because `bin/` contents become bare commands for every user with the plugin enabled (see finding 4's citation), `test-ag-claim.rb`, `ag-dev-link`, and `ag-sync` also land there. Fix: keep only `ag-claim`/`ag-dependents` in `bin/`; move dev/test scripts to `scripts/` or `dev/`.
17. **Doc drift in README and design docs.** "Claude Code is turn-based — a single command can't sit idle waiting" is now only half-true (`/goal` continues across turns; monitors and `FileChanged` hooks wait on events); the customisation design doc's "a skill cannot read its own session id" and "no programmatic session naming" are both superseded (findings 5). The design docs are dated drafts so this is expected, but the README sentence should be softened when Q1's recommendations land.
18. **CLAUDE.md section vs rules.** The ~30-line appended Agentile section is fine, but the memory docs recommend moving procedural content out of CLAUDE.md (target <200 lines) into rules or skills ([memory](https://code.claude.com/docs/en/memory#write-effective-instructions)); offering `.claude/rules/agentile.md` as the scaffold target keeps the user's root CLAUDE.md lean and the section independently updatable by future `/ag-init` runs.
19. **Dev-loop alternative to `ag-dev-link`.** The cache-symlink trick works but fights the install model. The docs now support **skills-directory plugins**: any folder under `.claude/skills/` with a `.claude-plugin/plugin.json` loads in place, no marketplace, with `/reload-plugins` for component changes ([plugins reference](https://code.claude.com/docs/en/plugins-reference#skills-directory-plugins)). That's a simpler officially-supported live mode; keep `ag-sync` as the distribution check.

## Further suggestions (beyond the four questions)

- **Subagent memory.** Give `ag-reviewer` and `ag-builder` `memory: project` so they accumulate codebase patterns and recurring review findings across sessions — a direct implementation of the methodology's "the system gets smarter" with zero new machinery ([subagents](https://code.claude.com/docs/en/sub-agents#enable-persistent-memory)).
- **Preload the playbooks into the agents.** The `skills:` agent field injects full skill content at startup ([subagents](https://code.claude.com/docs/en/sub-agents#preload-skills-into-subagents)); alternatively use dynamic context injection (`` !`cat .agentile/build.md` ``) in the skills so playbooks arrive pre-read instead of "check for the file" instructions every consumer must obey.
- **Dynamic context injection for state reads.** `ag-inbox`, `ag-wip`, and `ag-next`'s preamble steps could inject `` !`cat …/inbox.md` `` / `` !`grep -l "status: in_progress" …` `` so the data is in the prompt before the model acts — fewer tool round-trips, more deterministic ([skills](https://code.claude.com/docs/en/skills#inject-dynamic-context)).
- **`context: fork` for ag-retro.** The retro reads lots of git history; running it forked in a subagent keeps the digest out of the main context, matching its own "run heavy log commands so only your summary lands in context" instruction ([skills](https://code.claude.com/docs/en/skills#run-skills-in-a-subagent)).
- **Statusline.** A plugin `settings.json` can set `subagentStatusLine` ([plugins reference](https://code.claude.com/docs/en/plugins-reference)); a statusline showing `claimed: <slug> · WIP 2/2 · queue 4` would make loop state visible at a glance — strong fit for `/ag-wip`'s job.
- **Named arguments.** Skills support `arguments: [slug]` with `$slug` placeholders ([skills](https://code.claude.com/docs/en/skills#use-arguments)) — nice for `/ag-abandon <slug>` and `/ag-plan <spec>`.
- **`/batch` awareness.** The commands reference describes `/batch` (decompose a large change into units, each in its own worktree); `/ag-prioritise` output is nearly a `/batch` input. Worth a docs pointer for users wanting parallel fan-out today.
- **AGENTS.md interop.** For repos shared with other coding agents, `/ag-init` could detect `AGENTS.md` and follow the documented import pattern instead of appending to a CLAUDE.md that imports it twice ([memory](https://code.claude.com/docs/en/memory#agents-md)).
- **Channels** (CI pushing failures into a session) pair naturally with the verify stage once watch mode goes event-driven.
